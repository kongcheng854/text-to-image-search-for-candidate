# 本轮检索优化与验证

日期：2026-10-15。默认检索已切换到 `object-guard-multiobject-prompt-v1`，基础整句余弦检索仍可在页面或命令行对比。没有更换模型、增加外部 API 或重新编码图库。

## 实现内容

### 单一主要对象：对混淆对象进行软降权

在原句图片余弦分数之外，使用同一个 CLIP 文本塔编码 `a photo of a car.` 等对象描述，比较目标对象和常见混淆对象的分数：

```text
最终分数 = 原句余弦分数
         - 0.5 × max(0, 最强混淆对象分数 - 目标对象分数)
```

例如 car 与 bus/train/truck，bicycle 与 motorcycle/skateboard/wheelchair。它只调整排序，不硬删除图片，也不会因为图片同时含多个物体就把结果全部过滤。

### 多个明确对象：原句与自然照片模板融合

“杯子、餐盘、食物”等多对象描述不适合互斥类别惩罚，因此对原句与 `a photo of ...` 的文本向量各给 50% 权重，平均后重新 L2 归一化，再与图片向量计算分数。保留原句信号，避免只奖励物体出现而进一步稀释关系。

否定、选择、未识别到词表对象、hot dog / bus stop / train station 等易歧义复合词保持基础检索。问句和已有照片模板不重复加前缀；可选模板超过 77 token 或出现退化向量时，也回退原句。原始查询超过模型限制时仍明确提示用户缩短。

词表由应用自定义对象词和同义词组成，不是通用句法分析器，不包含任何图片 ID、固定查询答案或评测分数。运行时只读取图库索引和模型，不读取 `evaluation/` 下的查询或判断文件。

### 工程接入

- 对象原型在 CPU 上分批编码，启动时缓存整个图库的对象分数矩阵；后续查询无需重新编码图片。
- 复用图片 ID 数组，最终只进行一次分数排序；同分仍按 ID 升序。
- 页面默认优化检索，展开“检索设置”可切换基础检索。
- JSON 导出包含 `ranking` 版本/参数/词表摘要、`score` 最终排序分数、`clip_score` 原句余弦分数，以及模型与图库指纹。
- 索引仍是原有 1,000×512 图片向量，不需要重建。

主要代码：[query.py](../../src/query.py)、[ranking.py](../../src/ranking.py)、[search.py](../../src/search.py)、[encoder.py](../../src/encoder.py)。

## 如何选择方案

先在原有 25 条开发查询上比较：主体分数相加、混淆降权、两者组合、视图加权、文本模板及组合。候选公式和完整排名记录在 [development.json](development.json)。

直接叠加主体分数或全图视图未稳定改善。最终选择“单对象保守降权、多对象模板融合”，再通过生产代码对完整图库重新执行，结果在 [development-final.json](development-final.json)。所选方案的全部开发 Top 5 均在已有视觉判断池内，因此报告的是完整图库排名的指标，不是把未评分图片当成错误，也不是仅对已知候选池重排得到的指标。

提前写入 [新增 10 条查询](../validation-queries.json)，在 [selection.json](selection.json) 中记录查询摘要并固定核心规则和参数后运行验证。验证结果没有用于继续调权重；之后补充的复合词和数值退化回退属于通用正确性保护，没有改变这些查询的结果。

## 结果

“完整匹配”要求主体及显式条件均成立；“至少部分相关”表示主体或主要内容相关。评分沿用前一轮 0/1/2 口径，由助理逐图复核，不是独立人工金标准。新增验证共有 56 个去重的“查询—图片”组合，使用同一判断比较两个方案。

| 数据 | 指标 | 基础检索 | 优化检索 |
| --- | --- | ---: | ---: |
| 开发 25 条 | 完整匹配 P@5 | 55.2% | **60.0%** |
| 开发 25 条 | 至少部分相关 P@5 | 89.6% | **94.4%** |
| 开发 25 条 | 池内分级 nDCG@5 | 0.8304 | **0.8684** |
| 新增验证 10 条 | 完整匹配 P@5 | 54.0% | **54.0%** |
| 新增验证 10 条 | 至少部分相关 P@5 | 82.0% | **94.0%** |
| 新增验证 10 条 | 池内分级 nDCG@5 | 0.8809 | **0.9337** |

开发集各类完整匹配 P@5：主体 92%→96%，动作 60%→64%，边缘/小目标 36%→40%，颜色 52%→60%，关系 36%→40%。首位完整匹配率没有变化：开发集 72%，新增验证 70%。

新增验证的改善主要是减少完全不相关的对象：

- V07“站在海滩上的鸟”：前五的风筝/纯海滩结果被其他鸟类图片替代。主体相关性提升，但街头鸽子、树上鸟仍未满足海滩条件。
- V09“蓝天下飞行的白色飞机”：风筝、滑雪跳跃被飞机图片替代；停在地上的飞机、红色飞机和灰天下的飞机仍不满足全部条件。
- V10“有叉子的餐盘食物”：真正的餐盘食物在前五中更靠前，装饰时钟更靠后。
- V01“黑狗”首位仍是黑猫，这个明确错误没有修复。

所以本轮改善集中在主体一致性和排序，尚未证明对新查询的完整动作、颜色或关系理解有提升。样本很小、来自同一个图库，指标不代表全库准确率、召回率或统计显著的普遍收益。

完整结果和指标：[validation.json](validation.json)、[validation-review.json](validation-review.json)、[metrics.json](metrics.json)。每条验证查询的原始/优化 Top 10 和共享复核图在 `sheets/V*-*.jpg`。

## 运行成本与验证

同一进程、同一模型、相同查询下，新增 10 条验证平均查询耗时约：基础 11.83 ms，优化 12.31 ms；优化进程峰值工作集约 571.87 MiB。首次模型加载、图库检查与文本原型准备约 5.26 秒。测量受缓存和系统负载影响，不将其视为精确性能承诺。

当前机器物理内存约 31.8 GiB，尚未在物理 8 GB 机器上验证。优化没有引入第二个模型或多视图库索引，资源开销仍较低。

29 项单元测试通过，包含原有索引完整性、路径校验、同分排序，以及新增词边界、同义词、否定回退、多对象保护、模板溢出与退化向量保护。浏览器验证检查页面与记录一致、切换两种检索、JSON 导出，以及空输入和超长输入；结果见 [browser-verification.json](../../examples/browser-verification.json)。

## 复现

```powershell
# 默认优化版
.venv\Scripts\python.exe -m src.search "A red car." --offline

# 原始基线
.venv\Scripts\python.exe -m src.search "A red car." --offline --ranking baseline

# 固定方案的开发集和新增验证运行
.venv\Scripts\python.exe -m scripts.verify_optimization
.venv\Scripts\python.exe -m scripts.summarize_optimization

# 重新生成题目要求的三组示例
.venv\Scripts\python.exe -m src.evaluate --offline
```

下一步值得单独比较更强的同尺寸编码器，以及真正保留坐标的局部对象/关系重排。本轮没有采用全图补边最大值、全图颜色直方图或跨模型向量平均。
